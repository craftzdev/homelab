# ADR-0012: バックアップ構成を実態に合わせ直す（Velero を採らない）

- **状態**: 承認済み
- **日付**: 2026-09-16
- **置き換え対象**: [ADR-0008](0008-backup-strategy.md)

## 背景

ADR-0008 は 3 階層（etcd / Velero / PBS）を決めた。
2026-09-16 時点で実態を調べたところ、**決めたものの大半が存在しなかった。**

| 階層 | ADR-0008 の記述 | 2026-09-16 の実測 |
| --- | --- | --- |
| 1: etcd スナップショット | 日次 | **一度も取られていない**。`scripts/etcd-snapshot.sh` は存在するが cron / launchd のいずれにも登録が無く、スナップショットファイルも 0 件 |
| 2: Velero | 日次・外部 S3 | **未デプロイ**（namespace も CRD も存在しない） |
| 3: PBS | 日次 VM バックアップ | ✅ 稼働中。6 VM・02:30・daily7/weekly4/monthly3 |
| snapscheduler | 誤削除からの Undo | **未デプロイ** |

さらに ADR-0008 は全体が **Ceph 前提**で書かれている。
Ceph は [ADR-0009](0009-drop-ceph-adopt-longhorn.md) で廃止され Longhorn に
置き換わったため、シナリオ表（S1/S5 の「Ceph replica で救えるか」）も
そのままでは読めない。

「3 階層ある」と書かれた文書と、「1 階層しか無い」現実が
2 週間以上放置されていた。**設計文書が実態と乖離していること自体が
最大の問題である。** 次に読む人は「バックアップは 3 重だ」と信じてしまう。

## 何が起きたか（この判断に至った経緯）

2026-09-13 のストレージ障害（[docs/storage-migration-2026-09-13.md](../storage-migration-2026-09-13.md)）の
調査で、以下が判明した。

- CNPG のバックアップ先はクラスタ内 MinIO で、その MinIO は **Longhorn の上**に
  あった。守るべき対象と同じストレージに載っており、ADR-0008 が
  「旧リポジトリの `minio-for-velero` はこの問題を抱えていた」と警告した形そのもの
- PBS は worker VM のディスクを日次で取っており、Longhorn のデータは
  ブロックイメージとしては保護されていた。**完全に無防備ではなかった**
- Longhorn の実データ 46.2 GiB のうち、**代替不能なのは 231 MB だけ**だった
  （moshitoku 200MB / umami 31MB）。残りは保持 15 日の監視データと
  CI で再ビルドできるコンテナイメージ

つまり穴は「バックアップが無い」ことではなく、
**きれいな DB バックアップの置き場所が 1 箇所だけ、しかも守る対象と同じ場所**
だったことである。

## 決定

### 1. Velero を採らない

ADR-0008 は Velero を階層 2 に据えたが、**導入しない。**

理由は、守るべきものが判明したから。namespace 単位で PVC を丸ごと
バックアップする仕組みは、231 MB の DB を守るには過剰である。
実際に守る必要があるデータは CNPG が自前のバックアップ機構を持っており、
そちらを使う方が復元も確実である（barman は PITR ができる。
Velero の PVC スナップショットはできない）。

ADR-0008 の階層 2 が意図した **S3（PVC 誤削除）と S5（ストレージの論理破損）**
のうち、S5 は下の 2. で塞ぐ。S3 は Git と CNPG バックアップで足りる。

> 導入しない判断であって、「いつかやる」ではない。
> やるつもりのものを書き続けるのが今回の問題だった。

### 2. CNPG のバックアップは Cloudflare R2 へ置く（→ S5, S7）

- 保存先: R2 バケット 2 つ（`homelab-umami-postgres` / `homelab-moshitoku-postgres`）
- 認証: **バケットごとにスコープしたアカウント API トークン 2 つ**。
  namespace が別なので、共有すると片方の侵害でもう片方のバックアップを
  消せてしまう。ユーザートークンは権限変更で黙って失効するため使わない
- 保持: 7 日（barman が R2 上の古いオブジェクトを自動削除する）
- 投入: `scripts/reconcile-cnpg-r2-credentials.sh`（1Password から読む）
- 費用: R2 無料枠 10 GB に収まる。**費用は判断材料ではない**

### 3. PBS を階層 3 として維持する（→ S5, S6）

- 対象: k8s ノード VM 6 台。ただし **control-plane の Longhorn ディスクは除外**
  （`backup=false`）。storage node は worker 3 台だけで、control の scsi1 は
  実使用 816K の空ディスクだった
- 保持: daily 7 / weekly 4 / monthly 3
- 構成管理: `scripts/reconcile-pbs-kubernetes-backup.sh --apply`

⚠️ PBS は 2026-09-11 から 5 夜連続で `No space left on device` により失敗し、
誰も気づかなかった。PBS 側の prune ジョブに保持条件が 1 つも設定されておらず、
何も削除されていなかったためである。現在は修正済みで、
`homelab.backup` グループのアラートが失敗・容量・停滞を検知する。

### 4. etcd スナップショットは「やる」と書かない

ADR-0008 は日次取得を決めたが、**一度も実行されていなかった。**

GitOps でクラスタは Git から再構築できる（[ADR-0002](0002-opentofu.md)、
[ADR-0006](0006-argocd-sops.md)）。etcd スナップショットは復旧を速くするが、
必須ではない。実行されない仕組みを「決定」として書き続けるより、
**現状は取っていないと明記する**方が正確である。

必要になったら `scripts/etcd-snapshot.sh` を launchd / cron に登録する。
その時点で本 ADR を更新する。

## 障害シナリオと現在の手当て

Ceph ではなく Longhorn を前提に書き直す。

| # | シナリオ | Longhorn レプリカで救えるか | 現在の手当て |
| --- | --- | --- | --- |
| S1 | ディスク 1 本 / ノード 1 台の故障 | ✅ 救える | — |
| S2 | Kubernetes リソースの誤削除 | ✗ | Git（宣言が残っている） |
| S3 | PVC の誤削除 | ✗ | DB は CNPG バックアップ。それ以外は **手当て無し**（下記） |
| S4 | etcd の破損・クラスタ全損 | ✗ | Git から再構築。**etcd スナップショットは取っていない** |
| S5 | ストレージの論理破損 | ✗ | ✅ **CNPG → R2**（検証済み）／ PBS の VM イメージ |
| S6 | ランサムウェアによる暗号化 | △ | PBS（別筐体）**のみ**。R2 は削除権限を持つトークンを使うため守れない。バケットロックを検討し、2026-09-17 に見送りを決定（下記） |
| S7 | 物理的な災害（火災・盗難） | ✗ | ✅ **CNPG → R2**（オフサイト）。他は手当て無し |

### S3 について明記しておく

DB 以外の PVC（Prometheus・Loki・Harbor・MinIO 等）を誤削除した場合、
**戻す手段は PBS の VM イメージからの復元だけ**である。
これは PVC 単位ではなく VM 単位の復元になり、粒度が粗い。

許容する。理由は、対象がいずれも再取得・再構築可能なデータであり、
そのために Velero を運用する負荷に見合わないため。

### S6 について明記しておく

barman は保持ポリシーの実行に削除権限を必要とするため、R2 のトークンを
書き込み専用にできない。**侵害されたクラスタは R2 上のバックアップを削除できる。**

PBS は別筐体で別認証なので、そちらが最後の砦になる。
R2 のバケットロックで塞げることを 2026-09-16 に確認した
（[r2-bucket-lock-2026-09-16.md](../r2-bucket-lock-2026-09-16.md)）。

- クラスタが持つ Object Read & Write のトークンでは、`object-lock` /
  `versioning` / `lifecycle` のいずれも 403 になる。**侵害されても
  ロックを解除できない**
- barman はオブジェクトを上書きしない（全キーが一意）。ロックは
  書き込み経路に触れない
- ただし保持期間は **6 日**にすること。`retentionPolicy: 7d` と
  同じ 7 日にすると barman が古いバックアップを消せなくなる

### バケットロックは入れない（2026-09-17 決定）

技術的には有効だと確認できたが、**適用しない。** 理由は次のとおり。

- **PBS が既に最後の砦として存在する。** 別筐体・別認証であり、
  クラスタを取られても残る。ロックはその上の二重化にすぎない
- 守る対象は 231 MB（moshitoku 200 MB / umami 31 MB）の DB データで、
  PBS の VM イメージにも含まれている
- 運用の結び付きが増える。ロック日数と `retentionPolicy` は
  「ロック < retention」を保つ必要があり、片方を変えるときもう片方を
  見落とすと、症状は「R2 の使用量が静かに増え続ける」形で出る
- **アカウント全体を取られた場合に守れるかは未検証である。** 確認したのは
  「クラスタのトークンでは触れない」ところまでで、R2 Admin トークンで
  既存オブジェクトの保持を短縮・解除できるかは調べていない

したがって **S6 は「PBS のみで受容する」** とする。表の ✗ は、
手当てが無いという意味ではなく、**R2 側には無い**という意味である。

> ⚠️ これは「調べていない」ではなく「調べた上で採らない」である。
> 手順は [r2-bucket-lock-2026-09-16.md](../r2-bucket-lock-2026-09-16.md)
> に検証済みの形で残してあるので、必要になったときの作業は数分で済む。

次のいずれかが起きたら再検討すること。

1. **PBS が使えなくなる**（故障・撤去・バックアップの停止）。
   そうなると R2 が唯一のクラスタ外コピーになり、
   それを消せる権限がクラスタ内にある状態は受け入れられない
2. **R2 に PBS が持たない種類のデータを置く**ようになる
3. `retentionPolicy` を延ばし、R2 を長期保管として使い始める

## 復旧目標

| 指標 | 目標 | 実態 |
| --- | --- | --- |
| RPO（DB） | 24 時間 | 日次バックアップ ＋ WAL アーカイブ。PITR は 7 日ぶん |
| RPO（その他 PVC） | 24 時間 | PBS 日次 |
| RTO | 4 時間 | IaC による再構築。**実測していない** |

## 検証

**バックアップは復元テストをして初めてバックアップである。**
ADR-0008 も同じことを書いていたが、実施された記録が無かった。

2026-09-16 に CNPG の復元検証を実施した（[記録](../storage-migration-2026-09-13.md) 追記15・16）。

| | 結果 |
| --- | --- |
| umami | ✅ 25 テーブル・サイズ一致。復元成功 |
| moshitoku | ✅ `cases` 17,274 / `case_observations` 26,903 等が本番と完全一致 |

### ⚠️ 検証で判明した落とし穴

**保存先を切り替えた直後の最初のバックアップは復元できない。**
両方の DB で同じ失敗をした。

```
encountered an error while checking the presence of first needed WAL
in the archive: 00000001000000020000002B: WAL not found
```

ベースバックアップが要求する WAL は切り替え**前**にアーカイブされており、
新しい保存先には存在しないためである。書き込み量とは無関係で、
アイドルな umami でも書き込みのある moshitoku でも同じだった。

また **`completed` の表示も、オブジェクトが存在することも、復元可能性を
意味しない。** 復元してみるまで分からない。

### 手順

保存先を変更したときは必ず以下を行う。

1. 新しい保存先へ向ける
2. 書き込みを起こして WAL を切り替える（`select txid_current(); select pg_switch_wal();`）
3. ベースバックアップを取る
4. **もう一度 WAL を切り替える**（endWal をアーカイブさせる。
   低書き込み DB では `archive_timeout` を過ぎても自動では切り替わらなかった）
5. 使い捨てクラスタへ復元して `COUNT(*)` で照合する
   （`n_live_tup` は復元時にリセットされるので使えない）
6. 上記が通るまで旧保存先を消さない

復元検証の具体的なマニフェストは
[docs/storage-migration-2026-09-13.md](../storage-migration-2026-09-13.md) §77 にある。

四半期に 1 度、CNPG の復元検証と PBS からの VM テストリストアを実施する。

## トレードオフ

- ❌ PVC 単位の復元ができない（S3 の粒度が粗い）
  → 対象が再構築可能なデータに限られるため許容する。
    DB だけは CNPG が PITR まで含めて担う
- ❌ etcd スナップショットが無いぶん、クラスタ全損時の復旧が遅い
  → Git から再構築できる。速度のために運用されない仕組みを増やさない
- ❌ R2 のトークンは削除権限を持つ
  → barman の保持ポリシー実行に必要。PBS を最後の砦とする
