# ADR-0001: ノード OS に Talos Linux を採用する

- **状態**: 承認済み
- **日付**: 2026-08-30
- **決定者**: クラフト

## 背景

既存リポジトリには Ubuntu 24.04 + kubeadm でクラスタを構築する資産
（`deploy-vm.sh`、Ansible ロール）があった。今回の要件は「**セキュアに**構築する」
であり、ノード OS の選定がセキュリティ水準を大きく左右する。

## 検討した選択肢

### A. Ubuntu 24.04 + kubeadm（既存資産の継続）

- ✅ 既存の `deploy-vm.sh` / Ansible ロールをそのまま使える
- ✅ トラブル時に SSH で入って調査できる（学習コストが低い）
- ❌ **汎用 OS であるがゆえに攻撃対象領域が広い**。SSH デーモン、パッケージ管理、
  systemd の各ユニット、シェル、cron —— これら全てが潜在的な侵入・永続化の経路
- ❌ CIS ベンチマーク相当のハードニング（`kubelet` 権限、カーネルパラメータ、
  auditd、ファイル権限）を**自前で書いて維持する**必要がある。書いた分だけ
  レビュー対象と劣化リスクが増える
- ❌ 構成ドリフトが起きる。誰かが SSH で `apt install` したら、その瞬間から
  「コードに書かれた状態」と実機が乖離する

### B. k3s on Ubuntu

- ✅ 軽量・シンプル。ホームラボで人気
- ❌ ノード OS の問題（A と同じ）が一切解決しない
- ❌ HA 構成（embedded etcd）は可能だが、Talos ほど枯れた自動化がない

### C. Talos Linux ★採用

- ✅ **SSH デーモンが存在しない。シェルも存在しない。パッケージマネージャも無い。**
  「ログインして操作する」という行為自体が定義されていないため、脅威 T4
  （ノード OS の侵害）の主要な経路が消える
- ✅ root ファイルシステムが **read-only の squashfs**。実行ファイルの差し替えに
  よる永続化が成立しない
- ✅ 全ての操作が **mTLS で保護された gRPC API** 経由。`talosconfig` の
  クライアント証明書が無ければ、ポートに到達できても何もできない
- ✅ **設定が単一の YAML（machine config）に集約される**。これは今回の要件
  「構築は常にコードで実装してリポジトリに管理」と完全に一致する。
  Ansible のような「手続きの集合」ではなく「あるべき状態の宣言」になる
- ✅ CIS Kubernetes Benchmark 相当の設定が**既定で適用済み**。
  自前でハードニングを書く必要が無い = レビュー対象とバグの余地が減る
- ✅ ディスク暗号化（LUKS2）、ingressFirewall、KubePrism が組み込み
- ✅ `talosctl upgrade` によるアトミックな A/B アップグレードとロールバック
- ❌ SSH で入れないため、**デバッグの作法を変える必要がある**
  （`talosctl logs` / `dmesg` / `read` を使う）。学習コストは実在する
- ❌ 既存の Ansible ロールは捨てることになる
- ❌ 任意のカーネルモジュールやツールを入れたい場合、Image Factory で
  system extension を組み込んだイメージを作る必要がある（ただしこれも
  宣言的にコード化できる）

## 決定

**Talos Linux v1.13.9 を採用する。**

決め手は、設計原則の第 1 項「攻撃対象領域を減らすことが、防御を足すことに優先する」
である。Ubuntu を CIS 準拠にハードニングするコードを書いて維持し続けるより、
そもそもハードニングすべき対象が存在しない OS を選ぶ方が、
**コード量が減り、レビュー対象が減り、劣化しない**。

また要件「構築は常にコードで実装」に対して、Talos の machine config は
「OS の全設定が 1 つの YAML」という理想的な形を提供する。Ansible の
手続き的なロール群より、意図が読み取りやすく、差分レビューしやすい。

## 結果として受け入れるトレードオフ

- 既存の `deploy-vm.sh` / `ansible/` は使わなくなる（Git 履歴には残る）
- 障害調査は `talosctl` に一本化される。運用手順書（[docs/50-operations.md](../50-operations.md)）
  に主要なコマンドを記載してカバーする
- 追加のカーネルモジュールが必要になったら Image Factory の schematic を更新する
  （`tofu/10-proxmox-talos/images.tf` でコード管理する）
